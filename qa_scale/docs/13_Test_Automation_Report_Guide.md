# מדריך דוחות וניתוח תוצאות אוטומציה (Test Automation Reporting & Analysis)

תהליך האוטומציה אינו שלם ללא מערכת דיווח מהימנה, ברורה ונגישה. מסמך זה מספק הנחיות מפורטות לשימוש בדוחות השונים, ניתוח נכון של כישלונות, זיהוי בדיקות מתנדנדות (Flaky) ושיתוף התובנות עם בעלי עניין בפרויקט.

---

## 1. הגדרה וניתוח דוחות Allure (Allure Report Guide)

**Allure Report** הוא כלי דיווח פופולרי, גמיש ומאוד ויזואלי, המאפשר לצוותי פיתוח, מוצר ו-QA לקבל תמונת מצב מהירה על בריאות האפליקציה.

### א. הגדרת Allure בפרויקט Playwright
כדי להשתמש ב-Allure, עלינו להתקין את חבילת ה-Adapter המתאימה:
```bash
npm install -D allure-playwright
npm install -D allure-commandline
```

לאחר מכן, נוודא שה-Reporter מוגדר בקובץ `playwright.config.ts`:
```typescript
reporter: [
  ['html'],
  ['allure-playwright', { outputFolder: 'allure-results' }]
]
```

### ב. הרצה והפקת הדוח
1. הרצת הבדיקות (התוצאות הגולמיות יישמרו בתיקיית `allure-results`):
   ```bash
   npx playwright test
   ```
2. הפקת דוח HTML מעוצב מתוך תוצאות הריצה:
   ```bash
   npx allure generate allure-results --clean -o allure-report
   ```
3. פתיחת הדוח המופק בדפדפן לצורך צפייה:
   ```bash
   npx allure open allure-report
   ```

### ג. כיצד לפרש את דוח Allure:
* **Overview (מבט כללי):** מסך הבית מציג עוגת סטטיסטיקה (Passed, Failed, Broken, Skipped), משך זמן הריצה הכללי ומגמות היסטוריות (Trends) אם מוגדר ב-CI/CD.
* **Categories (קטגוריות):** מאפשר למיין את הכישלונות לסוגים (למשל: תקלות תשתית/סביבה מול שגיאות קוד ובאגים אמיתיים).
* **Suites (חליפות בדיקה):** מציג את הבדיקות בצורה היררכית לפי התיקיות והקובצי `spec` שבהם הן נכתבו.
* **Graphs (גרפים):** מספק אינדיקציות גרפיות על חלוקת זמני הריצה של הבדיקות (הבדיקות האיטיות ביותר שמצריכות אופטימיזציה) ורמת החומרה שלהן.
* **Behaviors (התנהגויות):** מאפשר למפות בדיקות לפי תכונות ופיצ'רים של המוצר (במידה והוספנו תגיות כמו Epics / User Stories).

## 2. סיור בדוח ה-HTML המובנה של Playwright (Playwright HTML Report)

הדוח הדיפולטיבי של Playwright הוא כלי מדהים ומדויק לשימוש יומיומי עבור מפתחי האוטומציה.

### מאפיינים מרכזיים בדוח ה-HTML:
1. **סינון קל (Filtering):** ניתן לסנן במהירות לפי דפדפן (Chromium/Firefox/WebKit), סטטוס (Passed, Failed, Flaky, Skipped) או לפי חיפוש חופשי של שם הבדיקה.
2. **פירוט שלבים (Detailed Steps):** כל בדיקה מציגה עץ מתרחב של כל פעולות ה-Playwright שבוצעו בפועל (למשל: `page.goto`, `locator.click`, `expect.toBeVisible`), יחד עם משך הזמן המדויק שלקח לכל פעולה.
3. **שכבות מידע מצורפות (Attachments Area):**
   * **Screenshots (צילומי מסך):** תמונת מצב של המסך ברגע הכישלון המדויק.
   * **Video (הקלטת וידאו):** סרטון קצר המציג את תנועות העכבר, הקלדות המשתמש ותגובת הדפדפן בזמן אמת.
   * **Trace Viewer Link:** קישור ישיר לצפייה ב-Trace (מציג קריאות רשת, Console Logs ומצב ה-DOM לפני ואחרי כל שלב).

## 3. ניהול תוצרי דוחות ב-CI/CD Pipelines (CI/CD Artifacts)

כאשר בדיקות מורצות בשרת CI (כמו GitHub Actions, GitLab, או Jenkins), יש להגדיר שמירה של תוצרי הריצה (Artifacts) כדי שנוכל לחקור תקלות שקרו בשרת מרוחק.

### הנחיות עבודה ב-GitHub Actions:
* **איסוף תוצרים בכל מצב (if: always):** חובה להגדיר ששלב העלאת הדוחות יתבצע גם אם הבדיקות נכשלו, אחרת לא נקבל את המידע על הכישלון.
* **זמן שמירה (Retention Days):** מומלץ להגדיר שמירה של Artifacts למשך **14 עד 30 יום** כדי לא לחרוג ממכסות האחסון של הארגון אך עדיין לאפשר זמן חקירה הולם.
* **דוחות מונגשים (GitHub Pages):** בפרויקטים מתקדמים, מומלץ להגדיר שלב ב-Pipeline המפרסם באופן אוטומטי את דוח ה-HTML או ה-Allure אל GitHub Pages, כך שכל אחד מהצוות יוכל לפתוח את הדוח בלחיצת כפתור אחת בתוך ה-PR, ללא צורך להוריד קובצי `zip` מקומיים.

## 4. כיצד לקרוא ולנתח צילומי מסך של כישלונות (Failure Screenshots)

צילום מסך ברגע הכישלון הוא כלי עזר ראשון במעלה, אך יש לנתח אותו נכון:

* **האם הדף נטען במלואו?** אם בצילום המסך רואים מסך לבן או ספינר (Loader) מסתובב, הבעיה היא כנראה איטיות בשרת או חוסר בהמתנה יציבה (Timeout), ולאו דווקא באג פונקציונלי.
* **האם האלמנט נמצא מחוץ למסך?** לפעמים אלמנטים נמצאים מחוץ לטווח הראייה (Viewport). למרות ש-Playwright גולל אוטומטית אל האלמנט, ייתכן שרכיבים דביקים (Sticky Headers) מסתירים אותו.
* **האם מוצגת הודעת שגיאה ברורה של השרת?** לעיתים קרובות נראה צילום מסך של דף "500 Internal Server Error" או הודעת שגיאה אדומה המגיעה מה-Backend. במקרה כזה, יש לפתוח מיד את ה-Console Logs וקריאות הרשת (Network Calls) מה-Trace.

## 5. זיהוי וטיפול בבדיקות "מתנדנדות" (Flaky Tests)

**בדיקה מתנדנדת (Flaky Test)** היא בדיקה שמדי פעם עוברת (Passed) ומדי פעם נכשלת (Failed) על אותו קוד בדיוק, מבלי שנעשה שינוי מוצרי. בדיקות כאלו הן ה"אויב" מספר אחת של האוטומציה מאחר והן הורסות את האמון של המפתחים בתוצאות הבדיקה.

### שיטות לזיהוי בדיקות Flaky:
1. **שימוש ב-Retries (הרצה חוזרת):** בקונפיגורציה שלנו מוגדר `retries: 2` בסביבת ה-CI. אם בדיקה נכשלה בריצה הראשונה אך עברה בריצה השנייה או השלישית, Playwright יסמן אותה אוטומטית כ-**Flaky** בריצה הכללית.
2. **ניתוח זמני הרצה:** בדיקות שלוקחות זמן הרצה שונה באופן קיצוני בין ריצה לריצה הן מועמדות חזקות להיות Flaky (לרוב בשל בעיות סנכרון או המתנות קשיחות).

### כיצד לפתור בעיות Flakiness?
* **אבטחו את ה-Selectors:** הימנעו משימוש בסלקטורים ארוכים ומבוססי מיקום ב-DOM (כמו `div > div > ul > li:nth-child(3) > a`). השתמשו ב-User-facing locators כמו `page.getByRole('button', { name: 'Submit' })` או `page.getByTestId('submit-btn')`.
* **הימנעו מהמתנות קשיחות (Hardcoded Sleep):** לעולם אל תשתמשו ב-`page.waitForTimeout(5000)`. זוהי פרקטיקה גרועה מאוד המאטה את הבדיקות ועדיין אינה מבטיחה יציבות במקרה של עומס בשרת. במקום זאת, השתמשו בהמתנות מבוססות מצב כגון `locator.waitFor({ state: 'visible' })` או פשוט תסמכו על ה-Auto-waiting המובנה של ה-Assertions ב-Playwright (למשל `expect(locator).toBeVisible()`).
* **בידוד נתונים (Data Isolation):** ודאו שהבדיקות שלכם אינן תלויות בתוצאות של בדיקות אחרות ואינן משנות נתונים משותפים בבסיס הנתונים שיכולים להכשיל הרצות מקביליות.

## 6. שיתוף דוחות עם בעלי עניין (Stakeholders)

לא כולם בארגון יודעים או צריכים לקרוא שורות קוד של בדיקות, אך כולם רוצים לדעת "האם הגרסה יציבה?".

### התאמת המידע לקהלי יעד שונים:
* **למנהלי מוצר (Product Managers):** שתפו את הסטטיסטיקה הכללית מתוך Allure. דברו במונחים של "כיסוי פיצ'רים" ודוחות "Passed/Failed" ברמה העסקית, ללא צורך בהצגת לוגים טכניים של שגיאות JS.
* **לראשי צוותים ומפתחים (R&D Leads):** שתפו קישורים ישירים ל-Playwright Trace Viewer מתוך ה-CI/CD. הם צריכים גישה מהירה לקריאות ה-API שנכשלו (Network Tab) ולשגיאות ה-Console כדי לתקן את הבאגים מהר.
* **להנהלה הבכירה (Management):** הציגו מגמות שבועיות/חודשיות (Trends) של אחוז ההצלחות באוטומציה, זמן הרצה כולל שמתקצר, וחיסכון בשעות עבודה ידניות בזכות הבדיקות האוטומטיות שרצות בלילה.
