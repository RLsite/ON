# אסטרטגיית אוטומציה של בדיקות (Test Automation Strategy)

מסמך זה מגדיר את האסטרטגיה, המתודולוגיה והעקרונות המנחים לביצוע אוטומציה של בדיקות בארגון. מטרת האסטרטגיה היא להבטיח את איכות המוצר, לקצר את זמן ההגעה לשוק (Time to Market) ולייעל את עבודת צוות ה-QA.

---

## 1. מתי לבצע אוטומציה מול בדיקות ידניות (Automation vs. Manual Testing)

האיזון בין בדיקות ידניות לאוטומטיות הוא קריטי להצלחת פרויקט הבדיקות. לא כל דבר צריך או כדאי לאוטומט.

### מתי להשתמש באוטומציה (Automate When):
* **רגרסיה (Regression):** בדיקות שחוזרות על עצמן בכל גרסה או פריסה (Deployment).
* **בדיקות עומסים וביצועים (Performance & Load):** פעולות שלא ניתן לדמות באופן ידני בצורה יעילה (למשל, 10,000 משתמשים סימולטניים).
* **בדיקות מונעות נתונים (Data-Driven):** בדיקה של אותו תזרים עם מאות או אלפי קלטים שונים.
* **יציבות וקבועות:** תרחישים בליבת המערכת (Core Path / Smoke Tests) שאינם משתנים לעיתים קרובות.
* **בדיקות אינטגרציה ו-API:** בדיקות תשתיתיות המאפשרות זיהוי מהיר של תקלות בקצוות המערכת.

### מתי להישאר בבדיקות ידניות (Manual Testing When):
* **בדיקות חקרניות (Exploratory Testing):** בדיקות המבוססות על אינטואיציה וסקרנות של הבודק למציאת באגים לא צפויים.
* **חווית משתמש ושימושיות (UX/UI Usability):** הערכת העיצוב, נוחות הממשק ותתי-גוונים של שפות ועימוד שקשה לאוטומט בצורה אמינה.
* **שלבים ראשוניים של פיתוח (Ad-hoc / Early Stage):** כאשר הפיצ'ר עדיין אינו יציב ומשתנה מדי יום – פיתוח אוטומציה בשלב זה יוביל לעלויות תחזוקה אסטרונומיות.
* **בדיקות חד-פעמיות (One-time tests):** בדיקות שלא יורצו שוב בעתיד.

## 2. פירמידת הבדיקות לאפליקציות Web (The Test Pyramid)

אנו פועלים על פי מודל **פירמידת הבדיקות** (Test Pyramid) כדי להבטיח פידבק מהיר, עלויות פיתוח נמוכות ויציבות מרבית.

```
       / \
      /   \      E2E (Playwright) - ~10% (Slowest, Expensive)
     /     \
    /-------\
   /         \   Integration / API - ~30% (Fast, Medium Cost)
  /           \
 /-------------\
/               \ Unit Tests - ~60% (Fastest, Cheapest)
-----------------
```

### א. בדיקות יחידה (Unit Tests) - ~60% מהכיסוי
* **מהות:** בדיקת פונקציות, קומפוננטות או מחלקות בודדות במנותק משאר המערכת (Isolated).
* **אחריות:** מפתחי התוכנה (R&D).
* **כלים מומלצים:** Jest, Vitest, Mocha.
* **זמן הרצה:** מילי-שניות בודדות לבדיקה.

### ב. בדיקות אינטגרציה ו-API (Integration / API Tests) - ~30% מהכיסוי
* **מהות:** בדיקת החיבור בין רכיבים שונים (למשל, אינטראקציה בין שירותים, בדיקת API Endpoints מול בסיס הנתונים).
* **אחריות:** מפתחים ובודקי אוטומציה.
* **כלים מומלצים:** Supertest, Postman, Playwright API testing.
* **זמן הרצה:** שניות בודדות.

### ג. בדיקות קצה לקצה (End-to-End Tests) - ~10% מהכיסוי
* **מהות:** סימולציה מלאה של תהליכי משתמש בדפדפן אמיתי (User Journeys) מקצה לקצה.
* **אחריות:** צוות ה-QA Automation.
* **כלים מומלצים:** Playwright.
* **זמן הרצה:** עשרות שניות עד דקות לכל בדיקה.

## 3. מדריך לבחירת כלי בדיקה (Tool Selection Guide)

לצורך פיתוח אוטומציית ה-UI וה-E2E, בחנו את שלושת הכלים המובילים בשוק כיום: **Playwright**, **Cypress**, ו-**Selenium**.

| קריטריון | Playwright | Cypress | Selenium WebDriver |
| :--- | :--- | :--- | :--- |
| **מהירות וביצועים** | מהיר מאוד (ארכיטקטורת WebSocket) | מהיר (רץ בתוך הדפדפן) | איטי יחסית (HTTP JSON Wire Protocol) |
| **תמיכה בדפדפנים** | Chromium, WebKit, Firefox | Chrome, Edge, Firefox (תמיכה מוגבלת ב-Safari) | כל הדפדפנים (באמצעות Drivers) |
| **תמיכה בטאבים וחלונות** | מלאה (Multiple Contexts) | מוגבלת מאוד | מלאה |
| **מנגנון המתנה (Waiting)** | אוטומטי ומובנה (Auto-waiting) | אוטומטי ומובנה | ידני (צורך במימוש Explicit Waits) |
| **ריבוי שפות תכנות** | TypeScript, JavaScript, Python, Java, C# | JavaScript / TypeScript בלבד | כמעט כל שפה (Java, Python, C#, JS, Ruby) |
| **הרצה מקבילית (Parallelism)** | מובנית, מהירה וחינמית | מובנית (חלק מהפיצ'רים בתשלום בענן) | דורשת הגדרת Grid מורכבת |
| **תמיכה ב-API Testing** | מעולה ומובנית | קיימת, אך מוגבלת | דורשת ספריות חיצוניות |

### החלטה:
בחרנו ב-**Playwright** ככלי המוביל של הארגון בזכות המהירות יוצאת הדופן, התמיכה המובנית בריבוי דפדפנים וחלונות, מנגנון ה-Auto-wait האמין שמקטין משמעותית בדיקות Flaky, והקלות של ההרצה המקבילית ב-CI/CD.

## 4. ארכיטקטורת תשתית האוטומציה (Framework Architecture)

תשתית האוטומציה מבוססת על העקרונות הבאים כדי להבטיח קוד קריא, מודולרי וקל לתחזוקה:

1. **Page Object Model (POM):** הפרדה מוחלטת בין לוגיקת הבדיקה (ה-Tests) לבין ייצוג דפי האפליקציה (ה-Selectors והפעולות על האלמנטים).
2. **TypeScript:** שימוש בטיפוסים חזקים (Strong Typing) למניעת שגיאות בזמן כתיבת הקוד ושיפור ה-Autocompletion ב-IDE.
3. **Layered Architecture:**
   * **שכבת הבדיקות (Test Layer):** קובצי ה-`*.spec.ts` המכילים תיאור תרחישים ו-Assertions בלבד.
   * **שכבת הדפים (Page Objects):** מחלקות המייצגות את ממשק המשתמש ומציעות מתודות עסקיות (למשל `login()`, `checkout()`).
   * **שכבת עזר (Helpers & Utilities):** פונקציות גלובליות לניהול תאריכים, חיבור לבסיסי נתונים, קריאות API ישירות להכנת נתוני בדיקה (Data Seeding).
4. **עקרון DRY (Don't Repeat Yourself):** הימנעות משכפול קוד של זיהוי אלמנטים או פעולות קבועות.

## 5. מדריך אינטגרציה ל-CI/CD (CI/CD Integration Guide)

האוטומציה היא חלק בלתי נפרד מתהליך ה-Continuous Integration. הבדיקות חייבות לרוץ באופן אוטומטי בכל שינוי קוד.

### אסטרטגיית הרצה ב-Pipeline (GitHub Actions / GitLab CI):
* **Pull Request (PR) Trigger:** הרצת בדיקות "Smoke" מהירות (ליבת המערכת, עד 5 דקות הרצה) על כל PR שנפתח. חסם למיזוג (Merge Block) במידה ויש כישלון.
* **Scheduled (Nightly) Build:** הרצת חליפת הבדיקות המלאה (Full Regression Suite) פעם ביום בלילה, כולל בדיקות קצה לקצה מורכבות, הרצה על דפדפנים שונים ואימות נתונים רחב.

### דוגמה להגדרת Workflow ב-GitHub Actions (`.github/workflows/playwright.yml`):
```yaml
name: Playwright Tests
on:
  push:
    branches: [ main, master ]
  pull_request:
    branches: [ main, master ]
jobs:
  test:
    timeout-minutes: 60
    runs-on: ubuntu-latest
    steps:
    - uses: actions/checkout@v4
    - uses: actions/setup-node@v4
      with:
        node-version: 18
    - name: Install dependencies
      run: npm ci
    - name: Install Playwright Browsers
      run: npx playwright install --with-deps
    - name: Run Playwright tests
      run: npx playwright test
    - uses: actions/upload-artifact@v4
      if: always()
      with:
        name: playwright-report
        path: playwright-report/
        retention-days: 30
```

## 6. יעדי כיסוי אוטומציה (Automation Coverage Goals)

כדי למדוד את אפקטיביות האוטומציה, הגדרנו את מדדי ה-KPIs הבאים:

1. **כיסוי תרחישים קריטיים (Critical Path Coverage):** 100% מתרחישי ה-Smoke (הרשמה, התחברות, רכישה, תשלום) חייבים להיות מכוסים באוטומציה.
2. **כיסוי בדיקות רגרסיה כלליות:** שאיפה לכיסוי של לפחות 75% מכלל מקרי הבדיקה הידניים המוגדרים כחשובים/בינוניים.
3. **יציבות הבדיקות (Success Rate):** אחוז הבדיקות הירוקות ב-CI/CD לא יפחת מ-95% (לא כולל תקלות תשתית זמניות).
4. **זמן הרצה כולל (Execution Time):** חליפת בדיקות Smoke לא תעלה על 5 דקות. חליפת בדיקות רגרסיה מלאה לא תעלה על 20 דקות (על ידי שימוש נכון בהרצה מקבילית).

## 7. אסטרטגיית תחזוקה (Maintenance Strategy)

כתיבת בדיקות היא רק חצי מהעבודה; החלק המאתגר ביותר הוא תחזוקת הבדיקות לאורך זמן.

### נהלים לטיפול בבדיקות נכשלות:
* **חוק "באג או בדיקה" (Bug or Test Issue):** עם קבלת התראה על כישלון ב-CI/CD, יש לנתח מיד האם מדובר בבאג מוצר אמיתי או בבעיה ביציבות הבדיקה (Flaky Test / שבירת סלקטור).
* **טיפול בבדיקות Flaky:**
  1. בדיקה שמכשילה את ה-Build ללא סיבה מוצרית ברורה תסומן מיד כ-`test.fixme` או תועבר ל-Skip על מנת שלא לחסום את ה-Pipeline.
  2. ייפתח כרטיס (Jira Ticket) ייעודי לתיקון הבדיקה עם עדיפות גבוהה.
  3. הבדיקה תוחזר לחליפה הפעילה רק לאחר שהוכחה יציבותה ב-10 הרצות רצופות בסביבת Sandbox.
* **קוד אחיד ומדריכי סגנון (Style Guide):** הקפדה על סקירת קוד (Code Review) גם עבור קוד האוטומציה, תוך שמירה על עקרונות ה-POM ושימוש בסלקטורים יציבים מבוססי נגישות (Accessibility Locators) כמו `getByRole` או `getByTestId`.
