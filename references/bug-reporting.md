# דיווח באגים — תבניות, טקסונומיה ו-Workflow

מתי להשתמש: בכל סגירת check עם `result:"fail"`, בכתיבת GitHub issue מהדשבורד, או
כשהמשתמש מבקש "תכתוב דוח באג מסודר".

## תבנית דוח באג (גם ל-note בדשבורד, גם ל-GitHub issue)

```markdown
## <כותרת: פועל + מה נשבר, ≤80 תווים>  (למשל: "שמירת דייר נכשלת כששם מכיל גרש")

**סביבה:** <אתר חי/גרסה vX.Y.Z> · <דפדפן> · <רזולוציה>
**מודול:** <login/forms/crud/...>   **חומרה:** <Critical/High/Medium/Low>   **עדיפות:** <P1-P4>

**צעדים לשחזור (Steps to Reproduce):**
1. ...
2. ...
3. ...

**תוצאה בפועל (Actual):** מה קרה, כולל טקסט השגיאה המדויק / מה שהוצג.
**תוצאה צפויה (Expected):** מה היה אמור לקרות.

**ראיות:** צילום מסך / שגיאת קונסול מדויקת / בקשת רשת שנכשלה (סטטוס+URL). לפי קטגוריה:
**performance** - מדד מדויק + תנאי הרשת (למשל "LCP 6.2s ב-Slow-3G throttle"); **security** -
ה-payload/ניסיון בפועל, לא רק תיאור מילולי; **API/אינטגרציה** - ה-request/response המדויקים
(curl אם אפשר).
**היקף:** קורה תמיד / לסירוגין (x מתוך y ניסיונות) / רק בתנאי מסוים.
**עקיפה (Workaround):** אם קיימת — מה המשתמש יכול לעשות בינתיים.
```

### כללי איכות לדוח
- **שחזור לפני דיווח** — שחזר לפחות פעמיים לפני שמסמנים FAIL. אם לא משוחזר, זה
  "לסירוגין" ומצוין ככזה עם ספירה.
- **מינימיזציה** — צמצם את הצעדים למינימום שעדיין משחזר (5 צעדים ולא 12).
- **עובדות, לא אבחנות** — "הכפתור לא מגיב, אין שגיאת קונסול" זה דיווח; "כנראה בעיה
  ב-event handler" זה ניחוש — אם כבר בדקת בקוד, הפרד: "נצפה: X. בדיקת קוד: Y".
- **באג אחד לדוח** — שני סימפטומים = שני דוחות (גם אם נראה שהשורש משותף).

## טקסונומיה — Severity × Priority (מוגדרים כבר בדשבורד)

| | תיאור | דוגמה |
|---|---|---|
| Critical | המערכת אינה שמישה / אובדן נתונים | האתר לא נטען; שמירה מוחקת רשומות |
| High | פונקציה מרכזית לא עובדת, אין עקיפה | אי-אפשר להוסיף דייר |
| Medium | תקלה עם עקיפה | ייצוא נכשל אבל אפשר להעתיק ידנית |
| Low | קוסמטי | יישור, פונט, רווח |

Priority נפרד (דחיפות תיקון): P1 מיידי · P2 גבוה · P3 בינוני · P4 נמוך.
שילובים לגיטימיים: Critical+P1 (רגיל), אבל גם Low+P1 (שגיאת כתיב בכותרת הראשית לפני
השקה) או High+P3 (פיצ'ר מרכזי שאף אחד לא משתמש בו עדיין).

## Bug Life Cycle (Jira-style workflow)

```
New → Assigned → In Progress → Fixed → Retest → Closed
                     ↓                    ↓
                  Rejected            Reopened → (חוזר ל-In Progress)
```

מיפוי לדשבורד שלנו (שהוא ה-tracker בפועל):
- **New** = check עם `result:"fail"` — ה-note הוא הדוח.
- **Fixed → Retest** = כשסוכן הפיתוח מדווח תיקון, נפתח check חדש "וידוא תיקון: <באג>"
  (לא עורכים את ה-FAIL המקורי — הוא נשאר תיעוד).
- **Closed** = ה-check החדש עבר PASS (כולל ניסיונות שבירה סביב התיקון — כלל 4c).
- **Reopened** = ה-retest נכשל **באותו תרחיש בדיוק** (אותם צעדים, אותה תוצאה שגויה, או תוקן
  רק בחלקו - למשל עובד ב-Chrome ולא ב-Safari) → FAIL חדש שמפנה לקודם ("Reopen של #NN").
- **באג חדש (לא Reopen)** = התרחיש המקורי עבר, אבל התיקון שבר משהו אחר / חשף תקלה שלא הייתה
  קשורה קודם → check חדש נפרד, עם note שמתחיל "נגרם על ידי התיקון ל-#NN" (זו תבנית ה-ripple
  של כלל 4b, רק שהמקור הפעם הוא תיקון ולא פיצ'ר חדש).
- ב-GitHub (אם מחובר): issue נפתח על FAIL, נסגר רק אחרי ה-retest PASS.
