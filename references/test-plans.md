# תוכניות בדיקה ותרחישי בדיקה

מתי להשתמש: כשהמשתמש מבקש "תכין תוכנית בדיקות ל-X", כשפיצ'ר חדש נכנס ואין עדיין
בדיקות בתור עבורו, או כשצריך לפרק בקשת בדיקה גדולה לתרחישים שאפשר להריץ אחד-אחד.

## תבנית תוכנית בדיקה (Test Plan) — קצרה ומעשית

```markdown
# תוכנית בדיקות — <שם הפיצ'ר/מודול>
| שדה | ערך |
|---|---|
| היקף | מה נבדק (מודולים/מסכים) ומה מחוץ להיקף |
| סביבות | אתר חי / local / staging + דפדפנים + רזולוציות |
| דרישות מקדימות | נתוני בדיקה, הרשאות, מצב מערכת נדרש |
| קריטריון כניסה | build יציב, deploy הושלם |
| קריטריון יציאה | כל התרחישים הקריטיים עברו; אפס Critical פתוחים |
| סיכונים | אזורים רגישים (נתונים אמיתיים, תשלומים, מחיקות) |
```

## עיצוב תרחישי בדיקה (Test Cases)

לכל תרחיש — מזהה, צעדים, תוצאה צפויה. פורמט לתור הדשבורד: תרחיש = בקשת בדיקה אחת
(`/api/add`), עם `module` + `category` מתאימים, והצעדים בתוך הטקסט.

```markdown
TC-<מודול>-<מס'> | <כותרת קצרה>
צעדים: 1. ... 2. ... 3. ...
צפוי: <תוצאה חד-משמעית שאפשר לקבוע עליה PASS/FAIL>
```

### כללי עיצוב תרחישים
- **תוצאה צפויה חד-משמעית** — "הטופס נשלח ומוצגת הודעת הצלחה", לא "עובד תקין".
- **תרחיש אחד = דבר אחד** — אם יש "וגם", פצל לשני תרחישים.
- **לכל happy path צֶמד שלילי לפחות** — על כל "התחברות תקינה" חייב להיות "סיסמה
  שגויה", "משתמש לא קיים", "שדה ריק". היחס הבריא: על כל תרחיש חיובי 1–3 שליליים.
  (זה הלקח מכלל 4c בסקיל — תור שכולו happy paths מייצר 100% PASS ריק מתוכן.)
- **פריסה על צירים** — כשהפיצ'ר רגיש לדפדפן/רזולוציה, שכפל את התרחיש הקריטי על
  הציר הרלוונטי בלבד (לא מכפלה קרטזית מלאה — בחר לפי סיכון).

### בנק תרחישים שליליים גנרי (להצמדה לכל מודול)
| קטגוריה | דוגמאות |
|---|---|
| קלט ריק | שדות חובה ריקים, רווחים בלבד, שליחה בלי כלום |
| פורמט | אותיות בשדה מספר, אימייל/טלפון/תאריך שגויים, ערך שלילי/אפס |
| גבולות | 0, 1, מקסימום, מקסימום+1, טקסט 500+ תווים |
| טקסט עוין | `<script>`, גרשיים, אימוג'י, עברית+אנגלית מעורבב |
| רצף | דאבל-קליק, רענון באמצע, Back, שני טאבים |
| מצב | מחיקת ישות שמוצגת במקום אחר, הרצה כפולה, בלי נתוני דמו |

## איך זה מתחבר לדשבורד
תוכנית בדיקות מאושרת ⟵ כל תרחיש נכנס כ-check בתור (FIFO), עם `module`, `category`,
ו-`browser`/`resolution` כשהם רלוונטיים. ה-traceability הוא דרך מזהה התרחיש בטקסט
(TC-LOGIN-003) — כך דוח ההרצה (ראה run-reports.md) יכול למפות חזרה לתוכנית.
