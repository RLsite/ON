## Recent Updates
- **Fixed the structural cause of Agent no-op responses on large files.** `github.read_file` previously returned only the first 50,000 characters, so the model could not see the active chat/UI code located later in the 220,000+ character `index.html`; it then edited the hidden legacy shell, narrated work without proposing an action, or stalled. Reads now support a focused `query` or a validated 1-400 line range, include total line/character metadata, and return an explicit first/last overview when an unfocused file is too large. The Agent can make up to two distinct read rounds, exact duplicate reads are stopped, and reaching the limit produces a clear no-change result instead of looping or pretending the request was completed.
- Extended the Agent contract end to end: code-change plans must include `github.update_version`, `github.create_pull_request`, and `github.deploy`. Approved execution updates the canonical version files, creates a PR from an `ontrack/agent-*` branch, and merges it into `claude/github-site-integration-fbb693`. Correction (see the entry below): this merge is a GitHub-only, git-level operation — it does not by itself update the running Cloudflare Worker. `on.rlapp.net` only picks up the change once a person separately runs `npm run deploy`.
- Added `github.apply_patch` to the central Agent validation allow-list so approved small file changes are no longer rejected after planning.
- Fixed Agent context loss after a repository read: the original current request is now included in the follow-up model call. Natural-language file-read intentions mentioning real repository paths are converted into safe read plans instead of being marked complete without execution. Previous chat history is not sent automatically without a separate user authorization.
- Added a `Refresh request` button to active, completed, and failed chat responses. It cancels an in-flight request before retrying it, prevents stale responses from overwriting the new attempt, and supports retrying saved text messages after a refresh.
- Clarified Agent plans: read-only `github.read_file` and `github.list_files` actions now show that no approval is needed, while `github.write_file`, `github.apply_patch`, and Pull Request actions show the approval flow. The read-results follow-up also gets one JSON repair attempt before the request is considered incomplete.
- Improved Agent reliability for NVIDIA NIM: the Worker loads the repository `AGENT_SKILL.md`, requires a strict JSON action contract, retries one malformed response, and rejects narration without executing it. Existing files can be proposed as small `github.apply_patch` diffs, avoiding full-file output limits; all writes remain approval-gated on a new branch.
- Added a visible chat-processing indicator: requests show sending, model processing, longer-running work, completion, errors, or an action plan waiting for approval. The indicator is available in Hebrew and English and does not claim a response is complete until the server returns it.
- Added per-Google-user Agent consent. The server stores the approved model, scopes, timestamp, and account-bound permission under a user-scoped key; changing models requires approval again.
- Activated the selected-model Agent flow: authorized requests receive repository context, read actions can return file context, and write plans require approval before a new branch and Pull Request.
- Added per-user chat history in Worker KV, restored after refresh, with an intentional clear-conversation action.

- **Fixed a critical Agent bug found in review, live on production:** a `github.write_file`/`github.apply_patch` action's own `branch` field was only checked for valid syntax, not restricted to the freshly created `ontrack/agent-*` branch — a plan could set it to `claude/github-site-integration-fbb693` (the live-serving branch) and, on a single "Approve and run" click, write directly to it with no Pull Request, no merge step, and no visibility into which branch was targeted (the approval card never showed it). Fixed by making every write always target the auto-created change branch, full stop — the field is no longer read at execution time. Also added a denylist rejecting any write to `.github/*` (workflow files, which could grant CI-level code execution) at both plan-validation time and again defensively at execution time.
- **Fixed the root cause of "the model doesn't update GitHub files":** a plan that was valid JSON but broke a contract rule (most commonly a code change missing one of `github.update_version`/`github.create_pull_request`/`github.deploy`) was silently dropped — the user saw only the model's own reply text, with no approval card and no error, because the specific validation error was computed but never surfaced and the `agentAccessRequired` flag it set was never read by the frontend. The model now gets one repair attempt with the exact rule it broke, and if it still fails, the actual reason is now shown to the user instead of a silent no-op.
- **Closed the approval-transparency gap:** the approval card previously showed only a tool name, file path, and a character count for a pending write — never the actual content or diff — so a human could approve a real GitHub write (and, bundled with `github.deploy`, a merge into the live branch) without ever seeing what it contained. The plan sent to the browser now includes a real content/diff preview (up to 8,000 characters, with a truncation note beyond that), rendered in the chat as a scrollable, monospace block.
- **Fixed the "deploy" naming, which overstated what actually happens:** `github.deploy` only merges the approved Pull Request on GitHub — nothing in the repo calls Cloudflare or `wrangler`, so the live site is not updated by this action. The agent's own system prompt, `AGENT_SKILL.md`, and the execution result now say so explicitly, so neither the model nor the UI implies the live site changed until a person separately runs `npm run deploy`.
- Fixed a pre-existing i18n mismatch: the Settings-panel display/theme button's Hebrew markup ("תצוגה") didn't match its `titleTheme` dictionary entry ("מצב בהיר / כהה"), which is what it actually does (toggle light/dark mode) — corrected the markup to match.
- Added a copy-to-clipboard button to every chat bubble (user and assistant), next to the existing delete button.
- Fixed a version-consistency bug in the fix above: bumping the app version only in this file doesn't change what the app displays — `index.html` has its own `const appVersion` plus two hardcoded markup defaults, and `package.json`/`package-lock.json` have their own copies. All four now stay in sync with this file's `Version:` line on every release.
- **Fixed the actual root cause of a real "the model doesn't update GitHub files" report.** The Agent's repair calls (both the JSON-shape repair and the contract-violation repair added earlier) used a smaller token budget (1,600) than the original attempt (2,600), even though a code-change repair has to re-emit the same full patch/content plus a reply plus up to four bundled actions — not smaller than the original, sometimes larger. At 1,600 tokens the corrected JSON likely got cut off mid-object, which the parser can't recover from, so the repair silently produced nothing and the request fell back to displaying the original, now-stale error as if no repair had been attempted. Both repair calls now get 2,600 tokens, the validation-repair prompt restates the full four-action bundle instead of only the single rule that failed, and the final error message now says plainly when a repair reply couldn't be parsed at all.
- Added a single automatic retry for a transient model-capacity error (HTTP 429/503/"rate limit"/"overloaded"), found from a real user hitting this while the fix above was being tested. Adversarial review found the first version of this retry could compound: one `/api/chat` request can chain up to 6 sequential model calls, and each could independently retry-and-wait, worst case ~7.2s of added delay plus up to 6 duplicated full generations on an already slow, non-streamed response. Fixed by sharing one retry budget across all calls in a single request, so at most one retry happens per request regardless of how many calls hit capacity errors. Also reworded the "still working" hint (previously blamed only "files or GitHub actions," misleading for a plain question hitting a hidden retry) and the capacity error message (now says explicitly when the one retry was already spent, instead of telling the user to do what the server just tried).
- A real approved write plan reached execution (the model produced a complete plan, the approval card showed the actual diff, the user clicked "Approve and run") and failed with GitHub's own `Resource not accessible by personal access token` error — but the message gave no way to tell which of the ~5 distinct GitHub calls in a write plan (reading the base branch, creating the change branch, each file write, the version-file updates, opening the Pull Request, merging it) produced it, and each of those needs a different token permission. Every stage now wraps its GitHub call and prefixes any failure with which stage it was ("Failed while creating the Pull Request: ..."), so a permissions problem points at the exact step — and therefore the exact scope to add to the connected GitHub token. (Root cause that time turned out to be an expired token, not a missing scope — the stage label is what let the user find that themselves.)
- A real Agent plan (approved, with a real diff shown in the preview) turned out to patch `index.html`'s hidden legacy `.oldApp` shell (`display:none`, never visible to any user) instead of the live `.newShell` UI it looks nearly identical to — a syntactically valid patch that would have passed every check, merged cleanly, and changed nothing a user could see. `AGENT_SKILL.md` (fetched and given to the model as context on every request) now explicitly names both shells, says which one is live, and requires confirming which container an element belongs to before proposing a change to `index.html` — matching class names alone (both have a `.railBrand`/`.brandMark`) isn't enough to tell them apart.
- After the fix above, the model correctly read `.newShell`'s brand-mark CSS before proposing anything — then announced the request was finished with no approval card ever shown and no write, PR, or merge ever made. Confirmed against the real repository (GitHub API: zero Pull Requests exist, open or closed). It described the change in a plain-text `reply` instead of proposing it as an `actions` entry — a distinct failure from "the model doesn't update files" (that one was a silently rejected plan; this one never became a plan at all). Both the live system prompt and `AGENT_SKILL.md` now explicitly forbid saying a change is done, made, applied, or complete unless the action that makes it is actually present in that same response.
- Re-audited per-user data isolation end to end, prompted by a direct question about it rather than a bug report — every KV resource added since the original global-key incident (workspace projects/libraries, agent consent, agent plans, chat history) plus every endpoint that touches them. Code-level adversarial review across 6 areas found the isolation intact everywhere, with one low-severity hygiene gap: two fully-implemented but completely unwired chat handlers (`handleLegacyChat`, `handlePlainChat`) that read/wrote per-user KV exactly like the live handler but sat outside the router's auth gate — not reachable today, but a real risk if ever wired in carelessly later. Removed both. Backed the code review with live two-real-user attack testing: seeded a real pending write-plan (with fake secret content) under one user's `agent_plan:<uid>:<planId>` key and confirmed the other user couldn't approve/execute it even with the real planId (rejected as expired — the lookup requires the caller's own uid, not just the planId); confirmed a user attempting to delete another user's chat message by its real ID silently no-ops instead of succeeding; confirmed concurrent writes by two users to every resource type never crossed into each other's data.
